# 文件共同撰寫工作流程

本 skill 提供一套結構化的工作流程，引導使用者進行協作式文件創作。請擔任積極的引導者，帶領使用者完成三個階段：脈絡收集、精煉與結構、以及讀者測試。

## 何時提供此工作流程

**觸發條件：**
- 使用者提到撰寫文件：「寫一份文件」、「起草提案」、「建立規格」、「寫起來」
- 使用者提到特定文件類型：「PRD」、「設計文件」、「決策文件」、「RFC」
- 使用者似乎正在開始一項大量的寫作任務

**初始提議：**
向使用者提議共同撰寫文件的結構化工作流程。說明三個階段：

1. **脈絡收集**：使用者提供所有相關脈絡，Claude 提出釐清問題
2. **精煉與結構**：透過發想與編輯，逐節建構文件
3. **讀者測試**：以全新的 Claude（無脈絡）測試文件，在其他人閱讀前揪出盲點

說明此方法有助於確保文件在其他人閱讀時（包括將其貼入 Claude 時）能良好運作。詢問他們是否想嘗試此工作流程，或偏好自由方式進行。

如果使用者拒絕，則以自由方式進行。如果使用者接受，則繼續進入第一階段。

## 第一階段：脈絡收集

**目標：** 縮小使用者所知與 Claude 所知之間的差距，讓 Claude 能在後續提供更聰明的引導。

### 初始問題

首先詢問使用者關於文件的後設脈絡：

1. 這是什麼類型的文件？（例如技術規格、決策文件、提案）
2. 主要受眾是誰？
3. 有人讀完後，希望達到什麼預期效果？
4. 有沒有要遵循的樣板或特定格式？
5. 有其他需要知道的限制或脈絡嗎？

告知他們可以用簡短方式回答，或以任何方便的方式傾倒資訊。

**如果使用者提供樣板或提到文件類型：**
- 詢問是否有樣板文件可以分享
- 如果他們提供共用文件的連結，使用適當的整合工具擷取
- 如果他們提供檔案，則讀取

**如果使用者提到編輯現有的共用文件：**
- 使用適當的整合工具讀取目前狀態
- 檢查沒有 alt text 的圖片
- 如果存在沒有 alt text 的圖片，說明當其他人使用 Claude 理解文件時，Claude 將無法看到它們。詢問是否要生成 alt text。如果是，請求他們將每張圖片貼入對話以生成描述性的 alt text。

### 資訊傾倒

一旦初始問題得到回答，鼓勵使用者傾倒所有擁有的脈絡。請求以下資訊：
- 專案／問題的背景
- 相關的團隊討論或共用文件
- 為什麼不使用替代方案
- 組織脈絡（團隊動態、過往事故、政治因素）
- 時間壓力或限制
- 技術架構或相依關係
- 利害關係人的顧慮

建議他們不用擔心整理——只需把所有內容說出來即可。提供多種提供脈絡的方式：
- 意識流傾倒
- 指向團隊頻道或討論串讓 Claude 閱讀
- 連結到共用文件

**如果有可用的整合工具**（例如 Slack、Teams、Google Drive、SharePoint 或其他 MCP 伺服器），提到可以用來直接拉入脈絡。

**如果未偵測到整合工具且在 Claude.ai 或 Claude 應用程式中：** 建議他們可以在 Claude 設定中啟用連接器，以允許直接從訊息應用程式和文件儲存空間拉入脈絡。

告知他們：一旦他們完成初始傾倒後，會提出釐清問題。

**脈絡收集過程中：**

- 如果使用者提到團隊頻道或共用文件：
  - 若有可用的整合工具：告知將立即讀取內容，然後使用適當的整合工具
  - 若無可用的整合工具：說明無法取用。建議他們在 Claude 設定中啟用連接器，或直接貼上相關內容。

- 如果使用者提到未知的實體／專案：
  - 詢問是否應搜尋已連接的工具以了解更多
  - 等待使用者確認後再搜尋

- 在使用者提供脈絡時，追蹤正在學到什麼，以及還有什麼不清楚

**提出釐清問題：**

當使用者表示已完成初始傾倒（或提供了大量脈絡後），提出釐清問題以確保理解：

根據脈絡中的缺口，生成 5-10 個編號問題。

告知他們可以用簡短方式回答（例如：「1：是，2：見 #channel，3：否，因為向下相容」）、連結到更多文件、指向頻道讓 Claude 閱讀，或繼續傾倒資訊。以任何對他們最有效率的方式即可。

**結束條件：**
當問題顯示已充分理解時，就表示已收集到足夠的脈絡——當可以在不需要解釋基礎知識的情況下詢問邊緣案例和取捨時。

**過渡：**
詢問是否還有更多脈絡想在此階段提供，或是否已準備好進入起草文件的環節。

如果使用者想要增加更多，讓他們繼續。準備好後，繼續進入第二階段。

## 第二階段：精煉與結構

**目標：** 透過發想、策選與反覆精煉，逐節建構文件。

**對使用者的說明：**
說明文件將逐節建構。對於每一節：
1. 會提出關於要包含什麼的釐清問題
2. 發想 5-20 個選項
3. 使用者指出要保留／移除／合併的內容
4. 起草該節
5. 透過局部編輯進行精煉

從最多未知數的那節開始（通常是核心決策／提案），然後完成其餘部分。

**章節順序：**

如果文件結構已明確：
詢問他們想從哪一節開始。

建議從最多未知數的那節開始。對於決策文件，通常是核心提案。對於規格，通常是技術方法。摘要節最好留到最後。

如果使用者不知道需要哪些節：
根據文件類型與樣板，建議 3-5 個適合該文件類型的節。

詢問此結構是否可行，或是否想要調整。

**一旦結構確認：**

建立初始文件結構，所有節都使用佔位文字。

**如果有存取 artifact 的權限：**
使用 `create_file` 建立 artifact。這讓 Claude 和使用者都有一個可以參照的架構。

告知將建立包含所有節的佔位文字初始結構。

建立所有節標題和簡短佔位文字（如「[待填寫]」或「[內容在此]」）的 artifact。

提供架構連結並說明現在要開始逐節填寫。

**如果無法取用 artifact：**
在工作目錄中建立 markdown 檔案。適當地命名（例如 `decision-doc.md`、`technical-spec.md`）。

告知將建立包含所有節的佔位文字初始結構。

建立包含所有節標題和佔位文字的檔案。

確認檔案已建立並說明現在要開始逐節填寫。

**對於每一節：**

### 步驟一：釐清問題

宣告將開始處理 [節名稱] 節。提出 5-10 個關於要包含什麼的釐清問題：

根據脈絡與節的目的，生成 5-10 個具體問題。

告知他們可以用簡短方式回答，或指出哪些是重要的。

### 步驟二：發想

對於 [節名稱] 節，根據節的複雜度，發想可能包含的 [5-20] 個事項。尋找：
- 分享的脈絡中可能被遺忘的內容
- 尚未提及的角度或考量

根據節的複雜度，生成 5-20 個編號選項。最後，如果他們想要更多選項，提議繼續發想。

### 步驟三：策選

詢問哪些論點應該保留、移除或合併。請求簡短的理由，以協助了解下一節的優先順序。

提供範例：
- 「保留 1、4、7、9」
- 「移除 3（與 1 重複）」
- 「移除 6（受眾已知道這點）」
- 「合併 11 和 12」

**如果使用者給出自由格式的意見**（例如「看起來不錯」或「我喜歡大部分，但……」）而非編號選擇，請提取他們的偏好並繼續。解析他們想要保留／移除／更改的內容並加以套用。

### 步驟四：缺口確認

根據他們選擇的內容，詢問 [節名稱] 節是否還缺少任何重要的東西。

### 步驟五：起草

使用 `str_replace` 將此節的佔位文字替換為實際起草的內容。

宣告現在將根據他們的選擇起草 [節名稱] 節。

**如果使用 artifact：**
起草後，提供 artifact 的連結。

請他們閱讀並指出要更改什麼。說明越具體，對下一節的學習越有幫助。

**如果使用檔案（無 artifact）：**
起草後，確認完成。

告知 [節名稱] 節已起草於 [檔名] 中。請他們閱讀並指出要更改什麼。說明越具體，對下一節的學習越有幫助。

**對使用者的關鍵指示（起草第一節時包含）：**
提供一個注意事項：請他們不要直接編輯文件，而是指出要更改什麼。這有助於了解他們的風格以用於未來的節。例如：「移除 X 子項目——已被 Y 涵蓋」或「讓第三段更簡潔」。

### 步驟六：反覆精煉

當使用者提供意見時：
- 使用 `str_replace` 進行編輯（永遠不要重新印出整個文件）
- **如果使用 artifact：** 每次編輯後提供 artifact 連結
- **如果使用檔案：** 只需確認編輯已完成
- 如果使用者直接編輯文件並要求閱讀：在心中記錄他們所做的更改，並在未來的節中記住（這顯示了他們的偏好）

**持續迭代**，直到使用者對該節感到滿意。

### 品質確認

經過 3 次連續迭代且沒有實質性更改後，詢問是否有任何內容可以移除而不失去重要資訊。

當節完成時，確認 [節名稱] 已完成。詢問是否準備好進入下一節。

**對所有節重複此流程。**

### 接近完成時

在接近完成時（80% 以上的節已完成），宣告打算重新閱讀整個文件並確認：
- 跨節的流暢性與一致性
- 冗餘或矛盾之處
- 任何感覺像「水字數」或通用填充文字的內容
- 每個句子是否都有份量

閱讀整個文件並提供意見。

**當所有節都已起草並精煉時：**
宣告所有節已完成。說明打算再審閱一次完整文件。

審閱整體連貫性、流暢性、完整性。

提供任何最終建議。

詢問是否準備好進入讀者測試，或是否想進一步精煉任何內容。

## 第三階段：讀者測試

**目標：** 以全新的 Claude（無脈絡污染）測試文件，驗證它對讀者是否有效。

**對使用者的說明：**
說明現在將測試文件是否真的對讀者有效。這可以揪出盲點——對作者來說有意義、但對其他人可能造成困惑的內容。

### 測試方式

**如果有存取 sub-agent 的權限（例如在 Claude Code 中）：**

直接進行測試，無需使用者參與。

### 步驟一：預測讀者問題

宣告打算預測讀者在嘗試查找此文件時可能提出的問題。

生成 5-10 個讀者實際上會問的問題。

### 步驟二：以 Sub-Agent 測試

宣告將以全新的 Claude 實例（無此對話的脈絡）測試這些問題。

對每個問題，以文件內容和問題啟動一個 sub-agent。

為每個問題總結讀者 Claude 答對／答錯的內容。

### 步驟三：執行額外確認

宣告將執行額外確認。

啟動 sub-agent 確認模糊之處、錯誤假設、矛盾之處。

總結找到的任何問題。

### 步驟四：回報與修正

如果發現問題：
回報讀者 Claude 在哪些具體問題上遇到困難。

列出具體問題。

說明打算修正這些缺口。

回到問題節的精煉環節。

---

**如果無法取用 sub-agent（例如 claude.ai 網頁介面）：**

使用者需要手動進行測試。

### 步驟一：預測讀者問題

詢問人們在嘗試查找此文件時可能會問什麼問題。他們會在 Claude.ai 中輸入什麼？

生成 5-10 個讀者實際上會問的問題。

### 步驟二：設定測試

提供測試說明：
1. 開啟全新的 Claude 對話：https://claude.ai
2. 貼上或分享文件內容（如果使用已啟用連接器的共用文件平台，提供連結）
3. 詢問讀者 Claude 所生成的問題

對於每個問題，指示讀者 Claude 提供：
- 答案
- 是否有任何模糊或不清楚的地方
- 文件假設讀者已知道的知識／脈絡

確認讀者 Claude 是否給出正確答案或有誤解。

### 步驟三：額外確認

同時詢問讀者 Claude：
- 「這份文件中哪些內容對讀者來說可能模糊或不清楚？」
- 「這份文件假設讀者已具備哪些知識或脈絡？」
- 「是否有任何內部矛盾或不一致之處？」

### 步驟四：根據結果迭代

詢問讀者 Claude 答錯了什麼或遇到了什麼困難。說明打算修正這些缺口。

回到問題節的精煉環節。

---

### 結束條件（兩種方式皆適用）

當讀者 Claude 能一致地正確回答問題，且不再提出新的缺口或模糊之處時，文件就準備好了。

## 最終審閱

讀者測試通過時：
宣告文件已通過讀者 Claude 測試。在完成之前：

1. 建議他們自行做最後一次閱讀——他們才是這份文件的主人，對品質負有責任
2. 建議再次確認任何事實、連結或技術細節
3. 請他們驗證是否達到了預期的效果

詢問是否想要再次審閱，或工作是否已完成。

**如果使用者想要最終審閱，請提供。否則：**
宣告文件完成。提供幾個最終建議：
- 考慮在附錄中連結此對話，讓讀者可以看到文件的發展過程
- 使用附錄提供深度內容，而不讓主文件過於臃腫
- 在收到真實讀者的意見後更新文件

## 有效引導的建議

**語氣：**
- 直接且有條理
- 在影響使用者行為時，簡短說明理由
- 不要試圖「推銷」此方法——直接執行即可

**處理偏離：**
- 如果使用者想跳過某個階段：詢問是否要跳過並以自由方式寫作
- 如果使用者似乎感到沮喪：承認這花的時間比預期的長。建議加快進度的方法
- 始終給予使用者調整流程的主導權

**脈絡管理：**
- 在整個過程中，如果某些提到的內容有缺口，主動詢問
- 不要讓缺口累積——隨時發現隨時處理

**Artifact 管理：**
- 使用 `create_file` 起草完整的節
- 所有編輯使用 `str_replace`
- 每次更改後提供 artifact 連結
- 永遠不要用 artifact 做發想清單——那只是對話

**品質重於速度：**
- 不要急於完成各階段
- 每次迭代都應做出有意義的改進
- 目標是一份對讀者真正有效的文件
