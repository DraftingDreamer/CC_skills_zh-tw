# Prompt Audit——找出並移除過時的 Prompt 撰寫模式

> **若您是透過 `/claude-api prompt-audit` 抵達此處：** 這就是正確的檔案。請依序執行以下步驟——不要把步驟內容摘要回覆給使用者。從 Step 0（確立範圍與目標模型）開始，並以產出兩項交付物作結：稽核報告（Step 5）與建議的 diff（Step 6）。

Prompt、skill 與工具描述會不斷累積針對舊模型調校過的指令：因為舊模型觸發不足而加上的強調語句、因為舊模型規劃能力差而加上的逐步指令碼、在 API 尚未提供 structured output 前寫下的格式鷹架。目前的 Claude 模型比起這些文字當初所針對的模型，更緊密、更照字面遵循指令，因此殘留的文字不只是浪費 token——特定的過時指令會主動使行為劣化（過度觸發、過度規劃、在模糊地帶給出生硬的回應），而單純不相關的文字則相對無害。因此，稽核的任務是找出**特定的過時指令**，而不是把 prompt 變短。這份稽核的準則是「每個 token 都要有存在的理由」，而不是「愈短愈好」。

**這份稽核一律會產出兩項成果：**

1. **稽核報告**：每一項發現都附上位置（`file:line`）、符合的模式、為何對目標模型而言已經過時，以及信心程度。
2. **建議的 diff**：針對值得處理的發現提出具體修改。只提出建議——未經使用者同意絕不逕行套用修改。

**最高指導原則：分辨過時內容與承重內容。** 若一項發現無法連結到下方任何一個具名模式，且理由沒有根植於目標模型的文件化行為，那就不算是一項發現。有疑慮時，把它以低信心程度標記在報告中，但不要放進 diff。不分青紅皂白地刪除，是稽核唯一會讓情況變得更糟的做法——見下方「不該標記的項目」，其約束力與模式表格相同。反過來同樣成立：**什麼都沒找到的稽核，就該什麼都不改**——乾淨的 prompt 涵蓋範圍本身就是有效的結果，空的 diff 勝過硬湊出來的 diff。

## Step 0：確立範圍與目標模型

**在讀取任何檔案之前，先從請求與 repository 本身確立以下兩件事——而不是用問的。** 這份稽核在設計上就是非互動式的：它在聊天 session、CI 作業或批次遷移中都以相同方式執行，因此它會陳述自己的假設並逕行進行，而不是暫停等待確認。兩項假設都會列在報告（Step 5）最上方，使用者可以透過用更窄的請求重新執行來修正它們。

1. **範圍。** 哪些檔案算在 prompt 涵蓋範圍內？若使用者的請求指名了檔案、目錄或檔案清單，那就是範圍。否則範圍就是整個工作目錄的 prompt 涵蓋範圍——也就是 Step 1 盤點所找到的一切。
2. **目標模型。** 過時與否是相對於模型而言的：在某一代模型上具有承重作用的權宜作法，到了下一代就是死重。依下列順序判定目標：請求中指名的模型；否則是 repository 所記載、進行中遷移的目的地（廠商筆記、遷移文件、TODO）；否則是 repository 自身程式碼或文件所指向的最新模型；否則是程式碼所呼叫供應商目前的旗艦代模型。若這次稽核是遷移工作的一部分，請連同本檔一併閱讀 `shared/model-migration.md` -> 對應目標的章節，因為每個遷移章節的檢查清單同時也是一份移除清單。

## Step 1：盤點 prompt 涵蓋範圍

找出所有以文字形式送達模型的內容，不只是名為「prompt」的那個檔案：

- **System prompt**，以及組裝它們的程式碼（f-string、範本檔、條件式區塊）
- **工具定義**——`tools` 陣列中的 `description` 欄位與參數描述
- **Skill 與規則檔**——`SKILL.md`、`CLAUDE.md`、`.cursorrules` 風格的規則檔、agent 指示檔
- **請求建構程式碼**——模型 ID、`thinking` 設定、取樣參數、stop sequence、prefill 建構、重試邏輯、beta 標頭
- **Few-shot 區塊與內嵌範例**，無論它們位於何處

在稽核之前，先列出您找到的內容，讓使用者能夠修正這份盤點清單。

## Step 2：確認出處

若有 git 歷史紀錄可用，對 prompt 檔案執行 `git blame`。對每一行強調或禁止性的文字，要問的問題是：**這一行防止的是哪個模型上的哪種失敗——而這個失敗在目標模型上是否仍會重現？** 為了緩解某個已不再使用的模型而加入的文字，預設應列為移除候選；沒有人能說明理由的文字，預設視為可疑。

即使沒有歷史紀錄，prompt 也能靠慣用語斷代。`<scratchpad>` / `<brainstorm>` 標籤指令、「think step by step」、assistant 輪次的 prefill、「先引用再擷取」的鷹架，以及 ROLE -> CONTEXT -> RULES -> EXAMPLES 樣板，全都標記著這是為遠更早期的 Claude 世代所寫的文字——這些手法如今若非已內化訓練於模型本身（thinking、經校準的拒答），就是已被 API 功能取代（structured output）。單靠慣用語斷代只是一個僅供標記的訊號（在 Step 5 的評分準則中屬於低信心）；唯有搭配一個根植於目標模型文件化行為的理由，才能提升到中或高信心——而一行把文字繫連到某個已退役模型年代的 `git blame` 記錄，正是這種搭配裡最有力的一種形式。

## Step 3：逐行分類——刪除規則

對每一條指令，只問一個問題：**模型會不會早就已經知道這件事？**

- **保留只有作者才知道的內容**：閱聽對象與產品、環境事實、品質標準、工具的契約與運作機制、真正困難的判斷取捨，以及限制背後的*理由*。這些是情境（context），而情境永遠不算過時內容。
- **可移除的候選項目**：重述訓練預設行為的文字（「be accurate and helpful」）、模型不必被提示就會做的行為（周全、規劃、使用工具），以及針對目標模型已不再具有的失敗所做的權宜措施。

第二個判準能讓第一個判準更銳利：這一行究竟是**對行為的限制**（刪除候選——請測試它），還是**模型無法從別處取得的情境**（通常保留）？這道檢查能防止稽核淪為比賽誰刪得多：天真的縮減作業，刪掉的往往正是價值最高的字句。

## Step 4：掃描反模式分組

依序檢視這四個分組。「訊號」列都是可以直接 grep 的——請對盤點清單執行這些訊號，而不是用肉眼掃視。

### Group 1——過時的 prompt 文字

#### 1a. 施壓語言——用平常的音量，說出您真正想說的

較舊、較難引導的模型確實需要強硬的措辭；現行模型對 system prompt 的反應非常敏銳，同樣的文字如今會用力過猛。這件事**雙向皆然**：誇大的強調會導致過度觸發與生硬的行為，而殘留的保留語氣（「try to」、「if possible」）如今則會被照字面解讀成「可以不用做到」的許可。

| 之前（針對舊模型撰寫） | 之後（現行模型） |
|---|---|
| `CRITICAL: You MUST use this tool when...` | `Use this tool when...` |
| `IMPORTANT: NEVER do X`（每份 prompt 裡出現好幾次） | 平實地陳述一兩個真正的限制，並附上理由 |
| `If in doubt, use [tool]` / `Default to [tool]` | *（刪除，或改為）* `Use [tool] when it would improve X` |
| `Be thorough. Do not be lazy. Do not stop early.` | *（刪除——現行模型預設就會主動積極）* |
| `Try to include a summary if possible`（當摘要其實是必要的時候） | `Include a summary.` |
| `You have a tendency to over-X, so...` / `Don't be too verbose` | 直接陳述期望的行為：`Keep responses to the length the question needs.` |

當好幾條指令都各自被標成 critical，這些標記就不再攜帶任何資訊——而且 prompt 的語域會變成輸出的語域：焦慮的 prompt 會產生謹慎、愛打預防針的模型。強調語氣本身並未被禁止；它是針對某條經證實權重不足的指令，測試過、範圍限定的修正手段，而不該是初稿就採用的語域。

**訊號：** 全大寫的 `MUST|NEVER|ALWAYS|CRITICAL|IMPORTANT` 密度；`!!`；旁邊沒有附上「because」的強調語氣；掛在真正需求上的 `try to|if possible|ideally`；`you (tend to|often|sometimes)` 這類特質論斷；`don't be too [adjective]`。

#### 1b. 被 API 功能取代的鷹架——用新功能替換，而非重寫

這些內容不是要調低強度，而是要換成取代它們的功能。若需要各模型的具體細節（哪個模型上會出什麼錯、確切語法），請閱讀 `shared/model-migration.md`。

| prompt 或請求程式碼中的鷹架 | 替代方案 |
|---|---|
| 「Think step by step」、`<scratchpad>`/`<thinking>` 標籤指令 | Adaptive thinking（`thinking: {type: "adaptive"}`）+ `effort`。在具備 thinking 能力的模型上，這句咒語充其量只是多餘；請透過設定而非散文來控制思考深度。 |
| 「Use the think tool to plan」／「plan before acting」 | 刪除——現行模型不必被告知就會規劃，這類文字反而會導致過度規劃。若清理後行為仍然過於躁進，請調低 `effort`，而不是加回散文說明。 |
| 「Show your thinking」／輸出中要求的推理區段 | 改透過 API 讀取 thinking 區塊。在 Claude Fable 5.1 上，指示模型重現推理過程可能觸發 `refusal`（推理擷取）——遷移時這是一項明確的稽核項目。 |
| Assistant 輪次的 prefill（`{"role": "assistant", "content": "{"`）以及圍繞它、用來強制輸出 JSON 的整組機制：stop sequence、正規表示式擷取、剖析失敗重試迴圈、「output ONLY valid JSON」 | Structured output（`output_config.format`）。在 4.6 以後的 Opus 級與 Sonnet 級模型，以及 Claude Fable 5.1 上，prefill 會回傳 400——在指出這個錯誤之前，請先到 `shared/model-migration.md` 對應目標的章節確認。若確實適用，*周邊的程式碼*同樣算過時內容——請稽核請求建構程式，而不只是 prompt 字串本身。只有**位於末尾**的 assistant 輪次才算 prefill——不論看起來是部分還是完整（以 assistant 端收尾的 few-shot 區塊仍算數）：陣列中間的 assistant 輪次只是普通的對話歷史，必須保留。 |
| 「每 N 次工具呼叫就摘要一次進度」的編排；硬性字數上限（`at most N words`） | 刪除並重新設定基準：現行模型會恰如其分地敘述進度，而輸出上限會在困難問題上餓死推理過程。比起針對舊模型的囉唆程度調校出來的數字上限，更該用質性的長度指引（「be concise」）。 |
| 內嵌的查表、計點系統、模型必須自行計算的算術評分規則 | 把資料放進檔案或工具結果；算術運算寫在程式碼裡。把判斷這一層留給模型。 |
| `budget_tokens`、非預設值的 `temperature`/`top_p`/`top_k`、過期的 beta 標頭、已失效的 400 重試路徑 | 見 `shared/model-migration.md`——這些究竟是會硬性報錯，還是僅僅已棄用，取決於目標模型，因此請從該檔對應目標的章節取得錯誤與否的判斷，而不是憑記憶。若確實會報錯，其周邊的重試／權宜程式碼也一併可以移除。 |
| 強制工具使用——`tool_choice: {type: "any"}` / `{type: "tool", name: ...}`——以及藉由強制工具來輸出 JSON 的模式 | 在 `tool_choice: auto` 下、於 prompt 指令中指名工具（引導式），或改用 structured output（擷取式）。在 Claude Fable 5.1 / Claude Mythos 5.1（以及 Mythos Preview）上會回傳 400；在其他地方雖然可運作，但通常只是偽裝成別的形式的 prompt 指令——`strict: true` 能在 `auto` 之下維持 schema 保證。也請一併稽核其周邊「找不到工具就重試」的迴圈。 |

**訊號：** `think step by step|take a deep breath`；指令中出現 `<scratchpad>|<thinking>`；用來防護 JSON 的 `stop_sequences`；重試迴圈裡的 `json.loads`；請求程式碼裡的 `budget_tokens|temperature|top_p`；`every \d+ (tool calls|messages)`；`at most \d+ (words|sentences)`。

#### 1c. 過度規範——描述目標，而非方法

| 模式 | 為何現已過時 | 修法 |
|---|---|---|
| 針對判斷型任務的逐步編排（`STEP 1: ... STEP 2: ...`） | 針對先前模型所寫的 skill 與 prompt，對現行模型往往規定得過死，反而使輸出品質變差——模型自己規劃的方案通常勝過手寫指令碼 | 陳述結果、限制與驗證方式；只在順序真正重要的地方保留編號步驟 |
| 禁止事項清單（「do not X, never Y, avoid Z...」） | 描述成功比條列失敗更有效；針對一個模型原本根本不會犯的失敗提出禁令，反而可能把它*錨定*到那個失敗上 | 保留那些在目標模型上仍會重現的失敗所對應的禁令；其餘改寫成正向的意圖陳述 |
| 對範例過度索引：單一的黃金輸出；過期的 few-shot 區塊 | 具體範例是 prompt 中最強的訊號——模型會模仿其長度、語氣與結構，而針對舊模型所寫的範例，會把那個舊模型的行為凍結進新模型裡 | 提供幾個刻意呈現差異的範例，並標明僅供參考；刪除模型早已具備該判斷力的範例；保留那些真正用來固定格式敏感輸出形狀的範例 |
| 用密集項目符號與大量格式來給行為指引 | 項目符號會抹平優先順序、把規則和理由切開，而且 prompt 的格式會滲透進輸出的格式 | 參考資料用結構化呈現；行為指引用散文，並附上「因為」 |
| 填充內容：泛泛的美德（「be accurate, thorough, clear」）、以重複作為強化、大雜燴式的邊界案例、附帶逃生出口的限制 | 模型會把一切都當成可執行的訊號；附帶說明會被套用到不該套用的地方；重複的規則會讓模型花費力氣去調和用字；量體本身也會直接推高 adaptive thinking 的花費 | 話只說一次，說在對的地方；把心力放在困難的判斷上，而不是簡單的部分 |
| 評分者與 eval 用語（「you will be graded on...」、「hidden tests」） | 描述的是計分機制而非需求本身，會把心力推向「表現給人看」 | 陳述評分者會檢查的每一項需求；絕對不要描述評分者本身 |
| 混在任務規則旁邊的策略指導（「it's usually best to...」） | 作者的經驗法則在某些情境下是錯的，而模型自己的規劃通常更好 | 如果刪掉這句話不會改變什麼是合法的、或成功如何被衡量，那就是策略——刪掉它 |

**訊號：** 非脆弱性工作中出現的 `STEP \d`／編號式祈使句；連續 3 行以上的 `Do not|Never|Avoid`；`do not hallucinate`（請重新測試是否仍需要它——這裡的移除屬於低信心，而非有文件記載的危害）；單一內嵌的黃金輸出；跨章節出現的近乎重複句子；`Remember,|Again,|As stated above`；`grade|graded|rubric|hidden test`。

#### 1d. 化石——比自己所屬的模型活得更久的文字

| 模式 | 為何現已過時 | 修法 |
|---|---|---|
| 針對特定模型版本的權宜作法：格式修正、緩解過度拒答的軟化語句、重試提示、「known issue with [model]」註解、依日期而定的條件式指引 | 沒有人負責移除，於是 prompt 不斷累積每一代緩解措施的聯集 | 每項緩解措施都應點名（或能追溯到）它所修補的模型；若該模型已退役，就移除並重新測試 |
| 遷移相對語氣：「X now works differently」、「also counts」、「no longer」 | 這種文字其實是相對於模型從未見過的舊版 prompt 的一份 diff；相對語氣暗示著根本不存在的替代方案 | 寫得就像現行規則是唯一存在過的規則 |
| 修補堆積：大量狹隘的條件式規則，每一條都能追溯到單一事件 | 模型面對的是一座特例迷宮，而非一致的原則，並會在其間以不可預期的方式失敗；在既有堆疊上再加一行而讓 eval 分數變好，不代表這座堆疊本該存在 | 把原則一般化，或修好底層的情境；也要測試移除，不只測試新增 |
| 無人強制執行的指令：沒有任何程式路徑、eval 或審查者會檢查的規則——在應用程式自己的 transcript 裡明顯就被違反 | 若沒有東西會檢查它、也沒有人注意到，它就不帶任何訊號——而本可以做成 hook、allowlist 或 schema 驗證器的行為規則，用散文表達反而較不可靠 | 能用程式碼強制執行的就用程式碼強制執行；沒有東西強制執行、也沒有人會想念的，就刪掉 |
| 用來頂替情境的身分佔位句（「You are a helpful assistant」） | 角色句作為一句話式的焦點設定沒有問題；問題出在用身分陳述去*取代*閱聽對象、產品與品質標準 | 不要標記簡短的角色句；只在它是 prompt 給出的唯一情境時才標記 |
| 針對話多模型所寫的更新抑制語句：「hold all findings for the final response」、「don't narrate」、「no interim updates」 | 這是針對過度敘述的模型所調校的；有這些文字在，現行模型（尤其是 Claude Fable 5.1）反而敘述不足，而且 harness 可能根本沒有請求模型在工具呼叫之間的進度說明（`thinking.display: "updates"`） | 先移除並重新測試；若仍然需要更多敘述，改用一句具體的話說明*何時*需要面向使用者的文字（見 `shared/model-migration.md` -> 從 Claude Fable 5 遷移到 Claude Fable 5.1 -> 面向使用者的進度更新） |
| 反格式化規則：「never use bullets」、「no headers」、「no bold」 | 這是針對過度使用格式的模型所寫的；Claude Fable 5.1 本身格式化已經不足，這條規則如今反而剝除了讀者想要的格式 | 移除，或改成一條說明「何時適合使用格式」的規則（見 Claude Fable 5.1 遷移章節中條件式格式化的程式碼片段） |
| 每隔幾輪就重新插入一次指令（harness 以固定節奏重複「reminder: ...」） | 這是給會在長 session 中遺忘指令的模型用的記憶拐杖；現行模型只要說過一次指令就會記住，每次重複都要付出 token 成本，而且在 preserved thinking 的歷史編輯檢查下，日後若移除它就會被視為一次歷史編輯 | 移除重複並重新測試；若確實需要逐輪提醒，改以限定回合範圍（`clear_at`）的 system 訊息傳送——或放在工具結果之後的文字區塊——且絕不要刪除較早的副本 |

**訊號：** prompt 或註解中出現已退役的模型名稱（`claude-2|claude-3|claude-instant|3\.5|3\.7`）；`hold (all )?(findings|results)|don't narrate|no interim`；`never use (bullets|headers|bold)|no (bullet|header)`；以固定節奏出現的 `reminder:`；`before|after [date]` 條件式；掛在行為規則上的 `now|no longer|instead of`；沒有人記得理由的規則；`^You are (a|an) (helpful|expert)` 後面沒有接任何與任務相關的內容。

#### 1e. 禁止事項群集——依出處判斷，而非依模型「是否還需要它」

對一連串無條件的「never / don't / must not」文字，稽核方式是逐條詢問：**它是否附帶陳述的理由，或編碼了真實的商業／政策限制？**——而不是問「目標模型是否仍然需要這道護欄？」（後面這個問題會讓所有東西都被保留下來，因為說出口的東西沒有一句是*有害*的）。編碼了可觀察限制的禁令（退款上限、資料規則、合規用語、公司不得做出的承諾）應該保留，理想情況下理由就寫在旁邊。單純描述不想要的*輸出風格*、卻查無出處的禁令——被禁的字眼、口頭禪清單、針對舊模型習慣所寫的「don't start with 'Certainly'」——都算過時內容：把想要的風格正向地重述成一句話，若真有理由就附上。周圍圍繞著一群有正當理由的禁令，並不會替混在其中、查無出處的禁令洗白；請逐行分別判斷。

#### 1f. 輸出塑形編排——同一個模式，要連根拔除

固定的期中更新節奏（「after every third tool call, post a progress note」）、數字化的輸出上限（「under 120 words」、「at most five bullets」）與砍細節的指令，都是**同一個**過度限制模式的不同展現，是針對會囉唆、會離題的模型所寫的。它們必須*一起*移除：即便附上了業務理由（「queue throughput」、「supervisors skim」），也不會讓數字化的箍限就此值得保留——請把目標改寫成不帶數字的閱聽對象／結果框架（「replies are scan-able and answer only what was asked」），而任何真正對格式敏感的需求，則保留為格式指令，而不是字數限制。只移除節奏、卻保留上限，等於這個模式仍原封不動。

### Group 2——脆弱的 skill 檔案

Skill 檔案（`SKILL.md`、`CLAUDE.md`、規則檔）承繼了 Group 1 的一切問題，還加上自己特有的失效模式。Skill 的體積，是每次觸發都要繳的稅。

| 模式 | 為何現已過時 | 修法 |
|---|---|---|
| 冗長的 SKILL.md，解釋模型早已知道的事 | 每一段都必須說明自己值得付出的 token 成本；一般程式設計知識做不到這一點 | 逐段套用 Step 3 的刪除規則 |
| 錯誤的自由度 | 對判斷型任務給出精確指令碼，是限制過度；對脆弱操作用模糊散文帶過，則是限制不足 | 讓具體程度對應到脆弱程度：開放性的領域用散文式的經驗法則，只有在狹窄橋接點才用精確指令（`do not modify this command`） |
| 時近效應陷阱：把某一次 session 踩到的坑，編碼成永久規則 | 下一次 session 會繞開一個根本不存在的坑洞 | 保留一條規則之前，先問：這條規則會幫到最近大多數的 session，還是只幫到寫下它的那一次？ |
| 易變的具體細節：寫死的路徑、旗標、版本號、沒有查證日期的 API 說法 | 隨著程式碼持續發布，skill 會在事實層面逐漸腐朽；預設不會有任何東西重新查核它們 | 把架構、資料模型與工作流程編碼進去；把留下來的事實性說法對照目前的程式碼查證，當作稽核的一部分 |
| 時效性內容（「if before [date]...」、選項選單、SKILL.md 與參考檔之間重複的資訊） | 日期會腐朽；一堆替代方案的選單會稀釋重點；重複的資訊會逐漸各說各話 | 用「舊模式」章節取代日期；提供一個預設值加一個逃生出口；資訊只存放在唯一一個地方 |
| 歷史敘事：過去式、事件編號、PR 編號、釘死的模型名稱 | 一條規則的權威性來自它所規定的行為，而不是促成它的那起事件；釘死的模型名稱會在下一次發布後無聲劣化 | 陳述現行規則；捨棄考古細節 |
| 觸發案例條列：條列一堆意思相近的範例查詢，每漏掉一次觸發就再加一句 | description 會出現在每一個請求裡；條列式寫法對每一份 token 預算都是稅，而且泛化能力比意圖分類還差 | 為意圖命名出通用的類別；觸發／行為的區分見 Group 3 |

**訊號：** `SKILL.md` 無法一口氣讀完；寫死的路徑與版本釘選；指示檔中出現過去式；description 在 git 歷史中只增不減。

### Group 3——工具描述

**評判工具描述的準則是精確度與契約的正確性，而不是簡潔**——這正是「把它剪短」的直覺最常指錯方向的地方。詳盡的描述，是影響工具表現的目前為止最重要因素，而最常見的失敗是描述*不足*。在現行模型上真正改變的，是*哪些內容*該放進描述裡：契約與運作機制留下，行為引導與示範範例移出。工具描述就是一份 man page——這個工具做什麼、何時該用它（以及何時不該用）、每個參數的意義、注意事項、它不會回傳什麼。

| 模式 | 方向 | 修法 |
|---|---|---|
| 含糊的單行描述；沒有說明的參數；沒有「何時不該用」 | **描述不足——加強** | 至少 3 到 4 句以上；描述必須精確符合實際行為（契約與行為對不上，會把模型帶往任何 prompt 文字都救不回來的路徑） |
| `CRITICAL: You MUST use this tool when...` | 過度引導——調降 | `Use this tool when...`——針對觸發不足的模型所寫的觸發強化語句，如今反而導致過度觸發 |
| 描述裡的示範範例、假造的對話輪次、內嵌協定（編號工作流程、HEREDOC）——無論數量多寡，即使是那些「能實測拉高呼叫率」的也一樣 | 放錯地方——搬走 | 範例會限縮探索空間，且每個請求都要付出 token 成本；把教學材料搬去 skill／漸進式揭露；讓參數本身更具表達力（命名良好的 enum 就能傳達意圖） |
| 說教式交叉參照（`ALWAYS use X, NEVER use Y for this`）與夾帶行為指令（「after showing results, always recommend...」） | 放錯地方——搬走或刪除 | 描述是關於功能的契約，不是傳遞對話式指令的通道；對工具 X 的偏好要寫在 X 自己的描述裡，而不是散落在它的對手工具描述中 |
| system prompt 中出現工具名稱；與實際工具清單重複、可能因此失準的散文清單 | 重複——刪除 | system prompt 不該指名工具；這樣一來，啟用或停用某個工具就永遠不會留下懸空的參照。不要暴露在目前設定下無效的工具 |
| 幾乎重複、彼此重疊的工具；臃腫的回應酬載；30 個以上、一律預先載入的完整工具目錄 | 結構性問題 | 用數量更少、邊界明確的工具，並在兩者的描述中都寫明邊界；回應要高訊號密度；工具數量一旦超過數十個，就改用 tool search／延遲載入，而不是把每個 schema 都預先載入 |

**有一條刻意保留的區分：觸發文字不是行為文字。** 職責是路由的文字——skill frontmatter 的 `description`、觸發區塊——可以正當地帶有經校準的急迫語氣，因為 skill 目前普遍觸發不足；理想情況下，這種語氣應該是針對觸發 eval 調校出來的，而不是憑感覺。職責是行為的文字，則應該用解釋而不是用喊的。這兩者對 grep 而言看起來一模一樣，所以標記之前，請先依功能分類。

**訊號：** 少於約 3 句的描述（加強）；描述內用來引導行為的 `MUST|ALWAYS|NEVER`（調降）；描述中的假對話或示範範例（搬走）；system prompt 散文裡的工具名稱（刪除）。

### Group 4——請求設定與架構

同一次稽核經常會在過時 prompt 內容的旁邊，反覆挖出這些問題；即使它們不是 prompt 文字，也請一併回報。

- **API 化石**：在目標模型上會報錯或已棄用的參數與標頭——各模型的清單收錄在 `shared/model-migration.md`；把每份遷移檢查清單都當成一份移除清單來用。
- **對快取不友善的排序**：時間戳記、UUID、每位使用者不同的內容被插在穩定內容之上。請閱讀 `shared/prompt-caching.md` -> 靜默失效因素，並在這次稽核中執行該節列出的 grep。
- **算進情境裡的預算倒數**：把剩餘 token 數量呈現給模型看，可能導致模型提早草草收尾；請盡可能避免顯示這類資訊。
- **用 LLM 去執行一個確定性的計畫**：agent session 的 transcript 其實就是同一段迴圈主體重複 N 次；呼叫的輸入完全決定了輸出。**請主動執行這項檢查，不要等它自己冒出來**：在每一個 pipeline、批次作業或 agent 迴圈中，*數一數模型呼叫的位置*，並針對每一處問：它的輸入是否完全決定了輸出。路由、計數、正規化、篩選與格式化這些步驟，都該還原成一般程式碼；只在工作真正需要判斷力的地方（為模糊不清的剩餘部分分類、撰寫判斷式摘要），保留剛好一次模型呼叫。當確實存在一個判斷步驟時，把模型呼叫全部歸零就是矯枉過正——請指名那唯一該保留的呼叫。
- **多餘的專職 sub-agent**：把 sub-agent 名單／agent 設定本身當成一個獨立的稽核對象來檢視。兩個 agent 做同一件任務、用同樣的工具、prompt 幾乎一模一樣，差別只在某個篩選條件或酬載欄位，這其實該是同一個 agent，把那個差異當作輸入參數即可。修法是具體編修名單——刪除多餘的定義，把它唯一真正的差異併入留下來的那個 agent 的 prompt 或酬載中——並像任何其他發現一樣，以 diff 的形式提出，而不是留下一則建議性註記就算了事。
- **沒有 token 帳務**：若缺乏依各涵蓋面拆分的成本可見度，這裡列出的其他每一項問題都無從被看見。若使用者尚未建立帳務機制，建議優先新增——這是衡量任何清理成果的先決條件。

## 不該標記的項目——保留清單

一份只會說「刪除」的稽核，傷害的正是最認真照做的使用者。以下項目即使 grep 命中，也要保留：

1. **情境永遠不算過時內容。** 閱聽對象、產品、環境事實、品質標準、限制，以及它們背後的*理由*——這些只有作者才知道。過短的 prompt 會產生千篇一律的輸出，因為模型會用安全的預設值去填補空白；給模型的情境，寧可多於看起來必要的量，也不要少。
2. **過時內容不等於長度。** 傷害來自特定的過時指令，而不是來自篇幅本身。絕不要單憑字數就替刪除找理由。
3. **脆弱操作要保留精確的指令碼。** 在只有唯一一種順序是安全的地方（破壞性指令、驗證流程、合規步驟），低自由度、規定式的文字才是對的。撰寫 prompt 該投入的心力，應該與這項任務偏離模型自然行為的程度成正比。
4. **工具契約的細節要保留——而且往往還會增加。** 參數語意、限制、失效模式、工具不會回傳什麼。這份稽核從描述中移除的是引導語氣與範例，不是契約本身。
5. **針對現行、已證實失敗所下的禁令要保留。** 判斷依據是這個失敗在此情境下、在目標模型上是否仍會重現——而不是這句話是否符合「禁令」的句型。
6. **觸發／路由文字可以帶有經校準的急迫語氣**（見 Group 3）。該標記的是內文裡的用力喊叫，不是具有承重作用的觸發文字。
7. **用來固定格式、且輸出確實對格式敏感的範例要保留**，並標明僅供參考。
8. **正常運作中的重複不算過時內容。** 正在*發揮作用*的重複或重疊內容——同一份契約在兩個檔案中各寫一次、一個 prompt 原則上可以沒有它也行的示範範例、只是您會用不同方式組織的內容——這是重構上的偏好，不是過時模式。只要它沒有造成錯誤，且目標模型能自行調和，稽核就該不去動它；只有在重複的部分內容真的互相牴觸時，才提出去重複或整併的建議。「什麼都沒找到的稽核，就該什麼都不改」這句話也適用於此：面對乾淨的涵蓋範圍，就回報它是乾淨的。
9. **一行式的角色陳述沒有問題。** 只有在身分文字取代了真正的情境時，才標記它。
10. **刻意的重點回顧不算填充。** 在 prompt 結尾把少數幾項關鍵限制重述一次，是已知且合理的模式；反模式是散落各處的重複。
11. **重新設定基準有時也要加字。** 讓 prompt 配合新模型，有時反而代表要針對新模型的失效模式*新增*指引（見 `shared/model-migration.md` 中各目標模型專屬的「行為變化」章節）。稽核的任務是讓 prompt 與模型相符，這件事是雙向的。

## Step 5：產出稽核報告

每項發現一筆條目，格式如下：

| 欄位 | 內容 |
|---|---|
| **位置** | `file:line`（或 `file:line-range`） |
| **證據** | 逐字引用的原文 |
| **模式** | 上方符合的分組／表格列 |
| **為何過時** | 一到兩句話，將其連結到目標模型的文件化行為（「current models are proactive by default; this booster now causes over-triggering」） |
| **信心程度** | **高**——現行 Claude 文件中有記載，或在目標模型上會報錯。**中**——一致且廣泛觀察到的行為（例如對範例過度索引）。**低**——屬於經驗法則或慣用語斷代；只標記，不編輯。 |
| **動作** | `remove` / `rewrite`（給出替代文字） / `move`（說明搬去哪裡） / `replace-with-API-feature` / `add`（描述不足——修法是*增加*文字；請給出） / `flag`（不提出編輯建議） |

報告依信心程度排序，最高的排在最前面。開頭先摘要：各分組的項目數量，以及以散文說明影響最大的兩三項發現。無法連結到某個模式與目標模型理由的發現，放在最下方標成 `flag` 項目，或乾脆不列入。

**標記與修正的門檻。** 只要一項發現符合上方分組中某一列有記載的模式，它*就是*一項高或中信心的發現，必須附上具體的建議動作——`remove`、`rewrite`（附替代文字）、`move`，或 `add`。`flag` 只保留給兩種情況：沒有任何一列記載過的低信心慣用語斷代，以及超出這次稽核範圍的項目。不要因為某項發現「看起來不太嚴重」、「讀起來像是溫和的提醒」、「屬於產品判斷」，或「實測確實有幫助」，就把一個符合既有模式的命中降級成 `flag`——這些都只是使用者可能*婉拒*您所提建議的理由，不是您該保留不提的理由。一份正確辨識出模式、卻什麼都沒建議的稽核，只做完了一半的工作；使用者永遠可以拒絕一個他們不認同的 hunk，但他們無法接受一個您從未寫出來的修正。

## Step 6：產出建議的 diff

- 只納入動作為 `remove`/`rewrite`/`move`/`replace-with-API-feature`/`add`、且信心程度為**高或中**的發現。`flag` 與低信心項目只出現在報告中。
- 一項發現對應一個 hunk，讓效果可以歸因，使用者也能選擇性採用個別 hunk。
- 當一條指令仍有實際用途時，改寫勝過單純刪除：把它簡單地重新表達一次（「look before you delete」），而不是保留冗長的原文，也不是把這個顧慮整個丟掉。
- 唯有連所有引用到它的地方都一併處理掉，一次移除才算完成：斷言舊行為的測試、呼叫端與輔助函式、文件，以及每一處釘死的模型 ID（含 README 與規則檔）。在宣告 diff 完成之前，先對專案 grep 一遍被移除的符號與舊的模型 ID——一個 prompt 修好了，但它的 smoke test 卻仍斷言舊行為，那是一個壞掉的應用程式，不是稽核的戰果。
- 對於請求建構層面的模式（assistant 輪次的 prefill、stop-sequence 鷹架、取樣參數化石），diff 必須在*每一條*程式碼路徑上都*徹底消除這項能力*——修好之後，請求建構程式中不應再有任何路徑會產生過時的形狀（例如：不應再有任何可觸及的分支會產生一個位於末尾的 assistant 輪次）——而不只是重新接好目前的呼叫端。要納入被改動函式的每一個呼叫點，以及只為了服務舊機制而存在的剖析／重試輔助函式，並改寫斷言舊請求形狀的測試。
- 報告與建議的 diff 就是這次交付物——把兩者都完整產出後即止步。不要在稽核中途暫停詢問是否繼續，也不要在結尾詢問是否要套用：直接呈現 diff，讓使用者按自己的步調採用其中的 hunk。只有在請求本身明確要求套用變更時（例如「clean it up」、「remove the cruft」），才把編輯實際套用到檔案上，即使如此，也要讓 `flag`／低信心項目排除在套用範圍之外。

## Step 7：驗證——移除是一個假設，不是結論

- **要探測行為，而不是聽自我報告。** 對每一項有爭議的變更，在一份草稿副本上跑一次變更前後的小型行為檢查（若使用者已有 eval 套件就用那個；否則就建構一個能實際運用到該指令用途的最小探測）。問模型自己是否需要某條指令，不算是一種測量。
- 風險高的地方，**一次只改一項**，讓迴歸問題能歸因到正確的原因。
- **若刪減造成迴歸，就簡單地把它加回來。** 用最精簡的形式重新表達那條指令並重新探測——不要恢復冗長的原文。
- **刪除之前先檢查頻外相依關係。** 先在更大範圍的系統中 grep 這段確切的 prompt 文字——分類器、測試與 log 剖析器有時候會直接比對 prompt 字串。
- **每次模型發布都要重新稽核。** Prompt 是與模型綁定的產物；在某一代上具有承重作用的一行文字，到了下一代就是過時內容。`shared/model-migration.md` 中每新增一個遷移章節，就是再次執行這份稽核的觸發時機。
