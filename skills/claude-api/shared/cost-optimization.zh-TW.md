# 成本最佳化——降低每項已完成任務的支出

> **如果您是透過 `/claude-api cost-optimize` 進入此處：** 這是正確的檔案。請依順序執行以下步驟，而非把指南摘要回報給使用者——呈現分析報告、排名計畫和發現*本身就是*執行的一部分。從步驟 0 開始（確立範圍、品質標準和基準線），並以步驟 4 的兩個交付成果作為結尾：成本分析報告和變更。

API 支出的最佳化單位是**每項已完成任務的成本，而非每個 token 的成本**。價格較高的模型，若能在更少輪次內完成工作，可能才是更便宜的選項；而一個成本較低的模型在失敗後，仍然會對其 token 計費，然後是重試，再加上失敗帶來的任何下游成本。以下所有判斷都同時考量成本和品質。

槓桿分為兩種，步驟的順序至關重要：

- **免費贏**——prompt 快取、輸入 token 整理（包含 prompt 稽核）、迴圈整理、輸出 token 整理、批次處理——在不降低輸出品質的前提下降低支出。它們優先執行，快取永久保持開啟。
- **權衡**——預算、effort、模型選擇、多模型架構——以智慧換取成本。它們最後執行，因為每個都會改變模型能做的事，而過度調整會損失品質，這是免費贏從未觸碰的。

**此工作流程的位置**：`prompt-audit` 子命令（`shared/prompt-audit.md`）單獨稽核 prompt 面（prompt、skill、工具描述）；本工作流程是整體成本審查——請求形狀、快取、迴圈結構、輸出、批次處理、effort、模型——並將該稽核作為輸入整理中的一個子槓桿（§ 2.2）執行，而非重述其模式；一旦專案有了 eval，這些槓桿就成為爬山演算法——每次一個變更對照 eval，保留或還原（步驟 3）。

以下引用的測量預期值是 Anthropic 已發布執行結果的快照（來源在結尾）。它們是方向性的，並非保證——步驟 3 的驗證迴圈才能讓數字在此專案上成立——而且兩個來源都是即時擷取的——平台指南透過 `shared/live-sources.md`，cookbook 在以下來源章節中的 URL——凡是擷取的頁面與此快照不同，以頁面為準。

## 步驟 0：確立範圍、品質標準和基準線

**首先，確立三件事——從請求和能找到答案的存放庫中取得，使用者無法提供時則向使用者詢問。** 與 prompt 稽核不同，此工作流程在設計上是互動式的：當某個槓桿缺少情境，或某個步驟會花費真實金錢時，與使用者共同處理，而非假設。預期不會一次就完成稽核。在報告頂端陳述這三件事（基準線本身可能一開始就寫「等待步驟 1」）。

1. **範圍。** 如果請求指明了檔案或目錄，那就是範圍。否則範圍是專案呼叫 Claude API 的每個地方——請求建構器、agent 迴圈、批次工作。注意不同的流量類別（互動式路徑和夜間工作即使在同一個金鑰上也是不同的工作負載）：分析報告、排名和之後的每次驗證都按類別執行，而「每項任務的成本」在不同類別之間混合是沒有意義的。**同時確立程式碼目標的平台**（第一方 Anthropic API、AWS 上的 Claude Platform、Bedrock、Vertex 或 Foundry）——功能可用性各異，它過濾哪些槓桿甚至可以考慮。
2. **品質標準。** 找到專案針對其 LLM 呼叫的 eval、測試套件或結果檢查。若無，在報告中顯著說明：沒有 eval，就無法將節省與退步區分開來。不要停止——無論如何都可以安全地提出免費贏——但將每個權衡槓桿標記為「套用前需要 eval」，並詢問使用者可以提供什麼結果檢查。eval 只驗證它涵蓋的流量類別：對未涵蓋路徑上的槓桿也做同樣的標記。如果唯一的檢查是使用者自己的手動審查，它會把守免費贏——它永遠不能放行一個權衡。完整的無 eval 結局——包括可以解鎖權衡的最小 eval 方案——在步驟 3 中。
3. **每項任務的基準線成本。** 基準線是最便宜的誠實數字，按此順序：
   - **從歷史記錄中取得，免費**：若有 Admin API 存取權，從步驟 1 的使用量和成本報告向前計算基準線——報告提供金額，但每項任務的分母必須來自使用者或應用程式自身的日誌；或按任務匯總應用程式自身記錄的 `usage` 物件，而非按請求——四個 token 計數，各自有其費率：一般輸入、快取寫入（5 分鐘持續時間為輸入的 1.25 倍，1 小時為 2 倍）、快取讀取（輸入的 0.1 倍）和輸出——乘數結構如定價頁面公佈；擷取費率時確認。
   - **從基準執行中取得，需花費**：執行專案的 eval（或者在沒有 eval 的情況下，回放代表性的真實請求樣本）並以同樣方式匯總。這會花費真實的 API 費用：說明預期成本——從步驟 1 的 token 估算和即時定價，「估算——等待步驟 1」是可接受的初始答案——**並在執行前取得使用者批准。** 如果使用者拒絕支出，從程式碼和他們能從 Console 讀出的任何帳單數字估算基準線，標記為估算，並繼續。

   目前每個模型的費率，請 WebFetch `shared/live-sources.md` 中的**定價** URL——價格會變；不要引用記憶中的費率（如果定價擷取失敗，有效的實現費率來自用成本報告金額除以使用報告中匹配的 token 計數——相同模型、相同 token 類型）。要計算 prompt 和檔案中的 token，見 `shared/token-counting.md`（`count_tokens` 回傳計數而不執行推理）。對照任何已知的月帳單進行估算基準線的合理性驗證：差異通常意味著單輪估算遺漏了多輪歷史記錄增長。

## 步驟 1：分析 token 去向

分析報告可以是實測或估算的。當組織的存取權允許時進行實測；否則退而讀取程式碼。無論如何，有價值的槓桿由工作負載的形狀決定，而非由存在的清單決定。

### 實測——使用量和成本 Admin API（首選）

如果使用者有 **Admin API 金鑰**（`sk-ant-admin01-...`——與標準 API 金鑰不同的金鑰類型；個人帳戶無法使用——建立和範圍涵蓋在 Admin API 文件中，可從 `shared/live-sources.md` 中的**使用量和成本 Admin API** URL 到達），則取得真實數字而非估算。這些是報告讀取，而非模型呼叫——不消耗 token。完整參數和回應綱要：`shared/live-sources.md` 中的**使用量和成本 Admin API** URL。

- **Token 分析報告**：`GET /v1/organizations/usage_report/messages`，帶有 `group_by[]=model` 和 `bucket_width=1d`（預設頁面是 7 個每日桶——提高 `limit`，最多 31；`group_by` 維度也包含 `api_key_id`、`workspace_id`、`service_tier` 和 `context_window` 等）。每個結果精確分成下方槓桿所作用的數量：`uncached_input_tokens`、`cache_read_input_tokens`、`cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` 和 `output_tokens`。
- **金額分析報告**：`GET /v1/organizations/cost_report`（每日粒度，USD 以分為單位的十進制字串），帶有 `group_by[]=description`；按描述分組的結果攜帶結構化的 `model`、`cost_type`、`token_type` 和 `service_tier` 欄位——`token_type` 讓快取分割直接以金額可讀。程式碼執行出現在 `Code Execution Usage` 描述下；Priority Tier 成本不包含在此端點——透過使用量端點的 `service_tier` 維度追蹤。
- 資料在請求完成後約 5 分鐘內出現；持續使用時每分鐘最多輪詢一次。
- 各平台注意事項：Claude Enterprise（claude.ai）組織改用 Analytics API，而這些端點目前在 AWS 上的 Claude Platform 不可用——在那裡，請使用者從 Console 的使用量和成本頁面讀取總計並告知。

實測分析報告直接回答：實際快取命中率（`cache_read_input_tokens` 與未快取輸入的比較）、有多少流量已走批次層、輸入 / 輸出平衡，以及支出在模型、金鑰和工作區上的集中情況。**確認實測足跡與稽核的程式碼合理匹配**（相同模型、合理的數量級）：報告涵蓋整個組織，跨專案共享的金鑰會混合其流量——使每個專案的讀取（包括步驟 3 的切換後確認）無法歸因。在不匹配的情況下，對照程式碼估算進行協調，在存在分離的地方透過 `api_key_ids[]` / `workspace_ids[]` 範圍限定使用量報告查詢（成本報告不接受任一過濾器——它只按工作區透過 `group_by` 分段），並建議以每個專案的金鑰或工作區作為測量前提，在沒有這種分離的地方。最佳化工作量追隨稽核範圍的支出，而非組織整體。

### 從程式碼估算

沒有 Admin API 存取權（無 Admin 金鑰、Claude Enterprise 組織，或 AWS 上的 Claude Platform——其功能可用性由 `shared/claude-platform-on-aws.md` 涵蓋）——甚至有存取權時，對於沒有任何使用報告能顯示的結構性事實——讀取請求建構程式碼：

> **每個模型的預設值、參數支援和每個平台的功能可用性會隨發布而改變。** 對於任何「省略 `thinking`/`effort` 時會發生什麼」、「此模型是否接受 `effort`」、「它支援什麼等級」或「此功能是否在 Bedrock/Vertex/Foundry 上可用」的問題，從 SKILL.md -> Thinking & Effort、`shared/models.md` 或 `shared/platform-availability.md`（或即時 Models API）讀取答案——絕不要假設，也不要在本指南中硬編碼答案。

- **前綴**：系統 prompt 和工具綱要有多大，以及是否有任何動態內容（時間戳記、請求 ID）被插入其中？
- **參考資料**：每個請求中是否內嵌了文件或手冊？
- **工具**：有多少綱要 token，以及每個請求是否都需要每個工具？
- **迴圈**：有多少輪次深度，以及是否有龐大的工具結果跨輪次累積？
- **媒體**：圖片、PDF 或大型檔案是否以全尺寸進入情境？
- **輸出**：可見回應有多長，`max_tokens` 設定為多少？
- **模型和 effort**：哪個模型、哪種 effort，以及有沒有任何一個曾對 eval 進行調整？查看省略兩者時模型的行為（SKILL.md -> Thinking & Effort）——一個執行思考的未設定預設值是隱藏的輸出 token 支出項目。
- **快取**：是否已有 `cache_control` 斷點，實際的 `cache_read_input_tokens` / `cache_creation_input_tokens` 顯示什麼？
- **延遲容忍度**：是否有使用者在等待每個回應，或者某些工作可以批次處理？

### 首先詢問應用程式自身的使用日誌

在對估算進行排名之前，**詢問使用者應用程式是否已記錄每個請求的 `response.usage`**——如果有，請其貼上一天的代表性資料。這樣快取命中率、輸入 / 輸出分割和思考 token 支出就從猜測變成了測量，零 API 成本，它決定了以下哪個排名表層適用。如果應用程式尚未記錄使用量，注意新增它本身就是一個免費贏的差異（步驟 3），並繼續用程式碼估算。

**在沒有使用資料的情況下估算快取命中率。** 如果應用程式記錄請求時間戳記，模擬 TTL 行走：排序時間戳記，每當與前一個請求的間隔 <= TTL 時計為命中（讀取會更新條目），並對平台提供的每個快取 TTL 執行（見 `shared/prompt-caching.md`）——不同持續時間之間的差異是更長 TTL 槓桿對使用者真實流量的上限。如果只知道彙總量，用 Poisson 到達率近似：命中率約 `1 - e^(-lambda·TTL)`，其中 lambda 是每秒請求數。這兩種方法都優於將平均間隔與 TTL 比較，後者忽略了突發性。

### 對槓桿排名

在觸碰程式碼之前，對分析報告使適用的每個槓桿進行規模評估，以便對候選清單排序。**引用規模的方式取決於您擁有的資料**——估算和測量在報告中不應看起來相同：

| 可用資料 | 引用每個上限為 |
|---|---|
| Admin API 使用量 / 成本報告 | **金額範圍**，標記為 `measured`（已實測） |
| 應用程式端 `usage` 日誌，或僅使用者報告的帳單總計 | **佔當前帳單的百分比**，金額僅作為附注「（約以您的 \$X/月計算 \$Y）」——百分比是主張；金額是使用者自己的計算 |
| 兩者都沒有（純程式碼讀取） | **相對類別**——「最大 / 中等 / 小」或數量級範圍——無具體數字 |

**在規模評估之前，刪去目標平台不支援的任何槓桿**（`shared/platform-availability.md` 是唯一真實來源——不要假設第一方可用性延伸到 Bedrock、Vertex、Foundry 或 AWS 上的 Claude Platform）。無法在使用者平台上部署的槓桿不值得排名；改在「已跳過」下列出並附上可用性原因。

在適用的單位內，從步驟 2 中引用的實測（或估算）支出元件和測量預期值對每個槓桿進行規模評估——例如：

- **快取上限**：跨請求共享且位元組穩定的輸入支出——即將成為前綴——以 0.1 倍重新計費。（Claude Fable 5.1 為 0.025 倍——Claude Mythos 5.1 是否共享該費率在發布時尚未確定——所以其每項任務成本等於或低於下方引用的 Claude Fable 5 數字。）將實測的 `uncached_input_tokens` 與程式碼分析報告結合起來：每個請求獨有的酬載永遠無法快取，所以在酬載主導（或已快取良好）的工作負載上，這個上限是誠實的較小值。對照已發布的 agent 迴圈範圍進行合理性驗證（在 81% 到 90% 命中率下的 2.5 到 3.7 倍因子）。
- **批次上限**：沒有人在等待的標準層流量支出的 50%。按模型分組的分析報告無法看到這種分割——首先分段：按 `service_tier` 分組以找出已進行批次的部分，使用更細的 `bucket_width` 發現計劃突發，並詢問使用者哪些流量可以等待。
- **輸入整理上限**：去往參考資料、工具綱要或超大媒體的輸入支出份額，§ 2.2 槓桿會移除或延遲這些。
- **Effort / 模型上限**：應用於最大支出集中點的已發布權衡曲線——以範圍形式攜帶，因為品質成本要到 eval 執行後才能確定。

對相同 token 提出主張的上限（快取內嵌文件 vs 刪除它）是互斥的：無條件計算每個上限，排名，然後對它上方槓桿的重疊進行縮減，使候選清單永遠不能超過帳單總和。

呈現排名候選清單，附上每個數字背後的分析報告證據——標記為按節省上限排名，而非套用順序（步驟 2 的 § 2.x 編號決定順序）——並說明清單在何處停止：上限佔帳單一小部分的槓桿——或無法補回批准的執行和驗證所需的工作量——不值得進行一個 eval 週期，而且大多數槓桿不會在任何給定的工作負載上佔有一席之地（本檔末尾的「工作負載形狀 -> 槓桿」表是將分析報告對應到槓桿的地圖）。在小帳單上，誠實的候選清單可能是空的：「這裡沒有什麼值得改變」是一個成功的發現，而非失敗——請直白地報告。預期節省是計畫數字，而非結果——步驟 3 的測量才是結果。

## 步驟 2：按順序使用槓桿

當請求要求進行編輯時，可以直接套用免費贏（裸子命令呼叫尚未要求——請提議）。權衡槓桿（2.6 起）始終在陳述其測量的品質成本並只在使用者明確接受後才套用——絕不要靜默地以準確性換取成本。而且每次涉及模型的執行——基準線、每個槓桿的驗證遍——都會花費真實的 API 費用：在每次執行前取得明確批准並附上預期成本，或一次作為涵蓋它們的步驟 3 測量預算。

以下引用的定價乘數（快取讀取 / 寫入費率、批次折扣）截至撰寫時為最新——在計算任何上限之前，對照 `shared/live-sources.md` 中的定價 URL 確認。

### 2.1 Prompt 快取——優先，且保持開啟

Agent 任務的每一輪都重新發送整個不斷增長的對話——系統 prompt、工具定義、每一個先前的輪次——所以 40 輪任務會發送其第一輪 40 次，任務成本大致隨輪次數的平方增長。快取不會停止重新發送；它將已快取的所有內容重新定價為 0.1 倍。

關於設計和放置——前綴匹配不變性、依穩定性對輸入分類、斷點模式、反模式表——**閱讀 `shared/prompt-caching.md` 並遵循其工作流程**；不要臨時放置 `cache_control` 標記。與成本特別相關的要點：

- **測量預期值**：Anthropic 在每個模型和基準測試上測量到的最大單一槓桿——它在 81% 到 90% 的命中率下，將 agent 迴圈成本降低了 2.5 到 3.7 倍；一個小型問題分類 agent 的帳單僅靠快取就下降了 83%。
- **當許多獨立對話共享靜態前綴（或前綴層以不同速度變化）時，使用明確斷點**。自動快取只在一個對話內攤銷；在 cookbook 的實際案例中，靜態系統前綴上的一個明確斷點大致將一佇列獨立任務中每項任務的成本減半。agent 迴圈的穩健形狀——靜態前綴上的一個明確斷點加上尾部的頂層自動快取——以及自動快取單獨使用是純粹額外費用的情況，在 `shared/prompt-caching.md` § 自動 vs 明確斷點中。
- **當迴圈在輪次之間等待人工時，使用 1 小時快取持續時間。** 它以 2 倍而非 1.25 倍寫入，並在第一次防止的快取未命中上就值回了自身——未命中會以全價重新發送整個前綴並再次寫入。根據請求之間的開始到開始間隔決定（生成時間計入 TTL）——`shared/prompt-caching.md` § 選擇 TTL 中的表。
- **稽核任務中途的快取破壞者**：斷點上方的動態內容；在請求之間更改 `thinking` 或 `effort`（始終使訊息快取失效，在某些模型上也使工具 + 系統快取失效——`shared/prompt-caching.md` § 失效層級）；任務中途更改任務預算；每次情境編輯遍；切換中途對話的模型（快取是每個模型的）。
- **從使用量驗證，而非從程式碼審查——並在每次 prompt 組裝更改後重新驗證**：在預熱迴圈上，`cache_read_input_tokens` 應該主導一般的 `input_tokens`，而 `cache_creation_input_tokens` 應大約是一輪的量，而非整個對話。如果不是這樣，用 `shared/prompt-caching.md` § 驗證快取命中中的健康迴圈特徵和酬載差異方法尋找快取破壞者——除非工作負載的輸入主要是每個請求獨有的酬載（永遠無法快取），或未命中是並行批次工件（§ 2.5）；兩者都不是破壞者，也都沒有修復方法。
- **當沒有使用歷史記錄可讀時的快取探測**：為專案自身堆疊建立一個草稿指令碼，對其自身的代表性請求發送兩次完全相同的請求；列印所有四個使用量計量器（`input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens`、`output_tokens`）兩次；如果第二個請求的 `cache_read_input_tokens` 為零則以非零值退出。隨快取差異一起提供，讓使用者可以自己執行前後比較。它花費真實 token，可能執行專案的工具——只在常設批准規則下執行，如果請求的工具會修改狀態，請將其指向草稿環境。

### 2.2 輸入 token——漸進式披露

只發送模型完成任務所需的內容，讓它按需擷取其餘內容。每個子槓桿都有跳過條件；本節末尾的注意事項適用於所有。

- **每個 prompt 中的大型參考文件** -> 移至工具或 skill 背後，讓模型按需擷取章節。當大多數呼叫都查閱了大部分文件時跳過——快取前綴中的文件很便宜——或者當 eval 顯示模型現在必須去尋找的規則上的案例出現了失誤。
- **系統 prompt 中的工具摘要** -> 刪除它們。工具綱要已渲染到請求中；以散文重述它們只會膨脹前綴。
- **許多或龐大的工具綱要** -> 對很少使用的工具帶 `defer_loading` 的工具搜尋，這樣定義只在需要時載入。當綱要超過約 10K token 時才有回報（MCP 伺服器很快就能達到）；低於此值時，搜尋步驟是額外負擔。測量陷阱：token 計算端點拒絕伺服器工具——改從 `max_tokens: 1` 請求讀取計費的輸入（一個有費用但微小的模型呼叫：它在常設批准規則下）。
- **以全解析度的圖片和 PDF** -> 預先縮減到任務所需的解析度。視覺輸入按像素面積 token 化，每個約 28×28 像素的區塊大約一個 token，所以成本隨解析度而非資訊內容縮放；1280×720 是安全的預設值，可將圖片上限為約 1,200 個 token（目前公式——透過 `shared/live-sources.md` 中的 Vision 文件驗證）。
- **內嵌的大型表格和成果** -> Files API 加上程式碼執行：掛載檔案，讓模型在沙箱中計算，只有答案進入情境。當沒有什麼可提取或計算時跳過——沙箱往返只會增加 token（且沙箱容器時間在免費額度之後按小時計費）。
- **擷取的網頁** -> 網路擷取工具中的動態過濾讓模板文字不進入情境。
- **中間結果無關緊要的連鎖工具呼叫** -> 程式化工具呼叫從程式碼執行呼叫，只有過濾後的結果進入情境；其文件報告在 agent 搜尋基準測試中輸入 token 減少 24%，且得分更高。
- **廣泛的資料傾印工具** -> 優先使用窄型存取器（`get_policy(claim_id)` 優於 `get_all_policies()`），並給列表工具加上 `limit` / `fields` / `date_range` 參數。
- **無界的使用者提供輸入** -> 作為接收閘道的 token 計算端點（`shared/token-counting.md`）：先計算，然後截斷、摘要，或將超大酬載路由到 Files API。
- **Prompt 文字本身** -> 作為本步驟的一部分執行 `prompt-audit` 子命令（`shared/prompt-audit.md`）；其模式表是過時 prompt 文字的參考（本指南刻意不重述它們），其報告和提議的差異折疊進本工作流程的交付成果中。當 prompt 面很小且近期已稽核時跳過。為舊模型撰寫的 prompt 讓目前的模型過度工作：在一個客服 eval 上，為 Claude Opus 4.8 撰寫的 prompt 在 Claude Opus 5 上每張工單的成本多 36%，而準確性不變；稽核後，相同的 prompt 比未稽核的便宜 14% 且更準確（97% 的工單，從 92% 上升）。在 Claude Sonnet 4.6 到 Claude Sonnet 5 的遷移上，稽核以相同準確性降低了 14%。

**本節的注意事項**：較小的前綴不一定是更便宜的任務。延遲情境意味著模型可能花費探索輪次擷取它之前可以內嵌讀取的內容。對照 eval 驗證——在 cookbook 的工作負載上，將手冊包裝進工具在成本上與明確斷點設定相符，並還回了準確性。

### 2.3 Agent 迴圈整理——防止長迴圈複合

只有當分析報告顯示有大量累積結果的深度迴圈時才相關；短迴圈永遠不會觸發這些，而增加的機制是純粹的額外負擔。

- **情境編輯**（清除舊工具使用或思考）**是情境視窗工具，而非節省槓桿。** 每次清除遍都重寫快取對話，這與 prompt 快取相悖——在為平台文件測量的執行中，情境編輯的成本超過了它節省的。用它來在視窗中騰出空間；將觸發器設得足夠高，使清除保持不頻繁，並在少數幾次大批次中清除，而非每輪。
- **壓縮**（伺服器端的摘要並繼續編輯）需要足夠長的 session 才能達到其觸發器；在一次長分類執行中它觸發一次，又進一步削減了 38% 的帳單。用其 `instructions` 字串引導它，讓任務關鍵狀態在摘要中倖存。
- **在自然邊界的用戶端修剪**：當一個工作階段完成時，將龐大的工具結果折疊為一行摘要，保持訊息陣列在修剪之間位元組相同，使每次修剪是一次冷快取未命中，而非每輪新的未命中。
- **自包含龐大步驟的子 agent**：巢狀迴圈吸收其自身的大量工具結果，並傳回一行，可選擇使用更便宜的模型。當決策模型需要中間情境來正確判斷時跳過——注意子 agent 啟動一個新鮮前綴，與父 agent 沒有共享快取。

### 2.4 輸出 token

- **`max_tokens` 是安全底線，不是調整旋鈕。** 模型看不到它；達到它會在中途截斷回應，帶有 `stop_reason: "max_tokens"`。在 Anthropic 的程式碼執行結果中，16,384 個 token 的上限終止了 Claude Opus 5 嘗試的 15% 和 Claude Fable 5 的三分之一，它們都沒有解決——有上限的執行每次嘗試花費較少，但按比例購買了較少的解決方案，所以每項已解決任務的成本沒有改善。對 agent 工作將其設定為 64,000（在 `xhigh` 或 `max` effort 下為 128,000），對那麼大的回應進行串流，並將 `stop_reason: max_tokens` 視為失敗嘗試，而非在相同上限下重試。
- **要縮短可見回應**，在 prompt 中指定確切的輸出形狀，理想情況下附帶範例。要縮短推理，那是 effort 參數（§ 2.6）——不是 `max_tokens`。
- **作為內容感知提前退出的停止序列**：為模型在無法繼續時發出的哨兵（例如 `<CANNOT_REVIEW>`）登記停止序列，使其停止而非花費 token 說明原因。

### 2.5 批次處理

**請求中每個 token 享 50% 折扣，包含快取讀取和寫入**——折扣疊加。對於無人值守的 agent 工作（評估執行、回填、計劃工作），快取之後的第二大免費槓桿。

- 結果在 24 小時內非同步到達；該視窗是過期時間，而非 SLA。保持面向使用者的工作為同步。
- 批次請求是單次——無中途工具迴圈。工具迴圈有時可以透過提前預取其輸入，展平為一個可批次的請求；在 cookbook 的實際案例中，這以大約互動設定成本的一半執行，但這是架構決策，而非參數——它改變了模型的推理方式（展平執行不那麼穩固地保持其通過率），且並行批次內的快取命中是盡力而為。
- 不適用於 Managed Agents session（目前機制和可用性：`shared/live-sources.md` 中的**批次處理** URL）。

### 2.6 Effort 和預算——第一個權衡

從這裡往下，每個槓桿都以能力換取成本。在 eval 上一次一個變更地調整。

- **在觸碰模型之前先調整 effort**（在公開 effort 參數的模型上——查看 `shared/models.md` 或 `shared/live-sources.md` 中的 **Effort Parameter** URL）。Effort 在不改變模型的情況下縮放思考和工具呼叫深度。在單獨的 session 中測試每個等級——在 session 中途更改 effort 會使快取失效並扭曲比較。保持比較誠實的調整方式：
  - 除了 `output_config.effort` 之外，所有單元都位元組相同；整個過程中使用相同模型。在開始下一個設定之前，在一個設定下完成每個樣本請求，以穩定的順序，以便快取讀取在設定之間可比較——如果快取計量器在設定之間仍然有實質差異，說明這一點並將讀取加權偏向輸出端成本。
  - 包含使用者已知的困難案例：曲線在容易的任務上最平坦，而困難的尾部是較高 effort 賺回成本的地方。
  - **副作用閘道**：如果重播一個樣本請求會執行修改真實狀態的工具，請將重播指向草稿環境或先模擬那些工具；調整永遠不值得一次生產修改。如果那不可能，只調整可以安全重播的請求並說明這一點。
  - 將曲線讀為平（較低設定完成此工作負載的工作）、陡（較高設定正在賺回其成本——現在是一個測量數字而非恐懼）或混合（說明哪些任務翻轉了——那些是下方重新執行失敗策略的候選者）。一兩個任務的通過率差異，或分錢的平均成本，都在單次執行的雜訊範圍內；對策是在爭議中的設定下重複試驗，並附上其成本提供。
  - 曲線是按工作負載*和*按模型的。保持樣本和結果檢查在報告說明的地方，並在模型遷移、重大 prompt 更改或工作負載轉移後重新調整。

  按工作負載形狀的預期：
  - 研究和知識工作：幾乎平坦的曲線——在 Anthropic 的執行中（全部使用 Claude Fable 5），`low` 放棄了 1 到 3 分，換得三分之一到一半的每項任務成本；`medium` 在 70% 到 85% 的成本下與預設的準確性相符；在測量的四個基準測試中，預設沒有比 `medium` 取得任何可測量的收益。較低 effort 也更快（在一個研究基準測試上每個問題 4.5 分鐘對 7.9 分鐘）。
  - 長期程式碼：真實的權衡——Claude Opus 5 在 `medium` 放棄約 2 分，換得一半成本，在 `low` 放棄約 8 分，換得四分之一成本。
  - 推理上限工作（深度多子主題研究）：每個 effort 步驟帶來約 2.4 個評分標準分——那條曲線沒有免費的削減。

- **以較高 effort 重新執行失敗**——當工作負載有可用的失敗訊號（測試、檢查器、驗證器）時。以 `low` 執行所有，以預設重新執行失敗：在 Anthropic 的程式碼執行結果中，約 93% 以約 \$0.70 每項任務通過，而以預設全部執行時是 91.7% 對 \$1.39——相同通過率換一半成本，計算上廉價的失敗嘗試。從 `medium` 開始解決了約 94% 換約 \$0.95。使用這個方法是為了節省，而非提升，並把檢查器和失敗上雙倍的時鐘算進去。

- **任務預算**（模型看到預算並自我調整——這是省錢的預算控制）：從迴圈的第 90 百分位 token 使用量設定，然後收緊。預算是諮詢性的——它引導模型而非阻止它——所以在工作負載上驗證遵守情況。在程式碼上測量：一個寬鬆的預算放棄了約 2.7 個通過率分，換得 18% 的節省；最緊的允許預算放棄 4.4 分，換得 47%。低於 20,000 個 token 下限的預算被拒絕；非常緊的預算可能產生類拒絕行為；在第一個請求時設定一次預算——任務中途的更改使快取失效。在接入之前檢查模型可用性（beta，且並非每個目前模型都可用）——參數形狀、串流需求和支援的模型在本 skill 的 SKILL.md -> 任務預算（快速參考）和 `shared/model-migration.md` -> 任務預算中。

- **不節省每項任務金錢但限制損害的安全底線**：Managed Agents session 預算是硬性美元停止；工作區支出限制是整個工作區的最終底線。

### 2.7 模型選擇——刻意放在最後

模型選擇限制智慧上限，這就是為什麼它排在每個不影響智慧的槓桿之後。

- **以每項已完成任務的成本對候選者定價，在您自己的流量上**，包括較大模型在較低 effort 下——每 token 價格清單無法預測排名。在 Anthropic 的執行中，Claude Fable 5 在 `low` effort 下在深度研究基準測試上超越了 Claude Sonnet 5，同時每項任務成本約低 10%；在一個程式碼子集上，兩個模型都基本飽和，Claude Opus 5 與 Claude Fable 5 相符（91.7% 對 91.3%），約佔其成本的 60%。對於大多數 agent 工作負載，從 Claude Opus 5 開始。在另一個極端，Claude Haiku 4.5 以 Claude Opus 5 每個問題成本的十分之一，以 63% 對 92% 的準確性回答知識問題——它適合輸出可檢查的高量工作，而非長期 agent 迴圈。
- **對尾部定價，而非中位數。** 在工作負載最困難的十分之一上比較模型：在典型任務上每個模型看起來相似且最便宜的看起來最好，但帳單由廉價模型失敗的任務決定——即使什麼都不失敗，尾部也是金錢的去向（在一次 20 個問題的研究執行中，兩個問題佔了 43% 的支出）。
- **降級方法**：先在目前模型上調整 effort；如果 `low` 通過了 eval，降一個模型層級，**確認目標層支援哪些參數和 effort 等級**（SKILL.md -> Thinking & Effort），將 effort 重置為該層的預設值——不是一個硬編碼等級；預設值和支援範圍因模型而異——並從那裡重新向下調整（在沒有 `effort` 支援的層，只在其單一預設下評估）。每次一個等級，對照 eval——當沒有更便宜的層時，槓桿已耗盡；如此說明，而不是發明一個步驟。目前模型陣容和探索：`shared/models.md`；模型替換機制和每個目標的重大變更，見 `migrate` 子命令（`shared/model-migration.md`）。
- **兩個模型可以勝過一個，恰好在兩種測量形狀上**——兩者都是架構更改；像一個一樣驗證：
  - **顧問**（較便宜的執行者執行迴圈，在困難決策上諮詢前沿模型）：當兩個模型之間的能力差距很大，且執行者確實諮詢時才有回報。諮詢率是脆弱的變數——降低 effort 可能讓一個配對從在大多數任務上諮詢降到幾乎沒有，然後它的得分低於執行者單獨——而有效閘道諮詢需要一個廉價的訊號；讓執行者自己識別困難案例需要它所缺乏的判斷力。首先進行基準測試：在 Anthropic 的程式碼基準測試中，旗艦配對是測量到的最準確設定，但在 `medium` effort 下，在大致相同的成本下，處於前沿模型單獨的雜訊範圍內——在新增顧問之前先調整 effort 並對更強的模型定價。
  - **協調者**（前沿模型規劃並將大量工作委派給較便宜的工作者）：只有在有大量可委派工作時才有回報——許多獨立的部分，理想情況下超過任何一個情境視窗所能容納的。在比任何情境視窗都大的工作上，它在每個 effort 設定下的成本都比前沿模型獨自低 55%（低於其最佳得分 3 到 7 分）；在例行搜尋工作上，它作為尾部保險付出了回報（約一半的平均成本，第 90 百分位的三分之一），但在更困難的完整集上則相反。當工作是一條相依鏈，或適合單一情境時，協調者為計畫、交接和合併付費，而單一模型可以免費獲得——在測量的每種此類情況下，協調者的模型單獨在較低 effort 下表現更好。

## 步驟 3：套用、測量、保留或還原——每次一個槓桿

- 從排名候選清單往下決定哪些槓桿值得一個差異——但**按 § 2 順序套用候選槓桿**（免費贏 -> effort / 預算 -> 模型），而非按節省排名順序：排名決定納入和 eval 預算去向；§ 2.x 編號決定順序。每個值得納入的槓桿都成為**其自身的差異**（每個差異一個槓桿，使還原清晰且效果可歸因），套用後再測量：重新執行涵蓋該槓桿流量類別的 eval，並將通過率和每項任務成本一起對照先前保留的設定（第一個槓桿的基準線）讀取。節省金錢並還回準確性的槓桿不是最佳化——還原它並記錄原因。觸及 eval 未涵蓋路徑的槓桿無法透過您擁有的 eval 驗證：那裡的免費贏只在成本上測量，並說明；那裡的權衡保持為未套用的提案（步驟 0.2 的標記規則）。
- **一次性詢問測量預算，而非每次執行。** 以其總預期執行和成本呈現驗證計畫——effort 調整是幾個設定的幾次試驗——並作為預算批准；在批准的預算內，個別執行不需要新的批准。在即時流量上的影子執行大約使生產支出翻倍，在它執行期間：這是其自身的批准。
- **絕不在一個案例的波動上保留或還原。** 在批准的預算內重複試驗，直到決定超出雜訊。已發布的標準——約 50 個案例和每個設定至少 5 次試驗——是生產切換的標準；在重複試驗時，較小的專案 eval 對每個槓桿的決定是可接受的。驗證快取差異需要預熱的快取：按順序執行樣本並從第二個請求起測量，否則 1.25 倍的寫入主導，免費贏顯示為退步。
- **當使用者根本無法提供任何結果檢查時**：免費贏成為只測量成本的差異（或提案，如果沒有批准的支出），權衡保持為未套用的提案，攜帶已發布的預期值，並提供少數真實答案的手動前後對比抽查——使用者的審查把守免費贏，永遠不是一個權衡。對於 effort 調整，只測量成本的執行仍然值得提供：相同的矩陣沒有通過率欄，並排報告每個設定下每個任務的輸出——正是使用者需要在前面自己判斷品質的內容。在報告中直白說明哪種模式運行，不要發明一個評分器來填補空白。如果應用程式不記錄使用量，新增 `response.usage` 記錄本身就是一個免費贏差異，它是沒有 Admin API 金鑰時此後所有測量的管道。
- **最小 eval 方案**——可以解鎖一個權衡槓桿的最便宜的東西，使「需要 eval」成為下一步而非死胡同。提供與使用者共同建立：
  - **輸入**：一組約 20-30 個從生產日誌提取或由使用者撰寫的真實請求——足以做出每個槓桿的保留 / 還原決定（上方的約 50 個案例標準是為最終生產切換）。凍結它們；每個設定執行相同的集合。
  - **每個輸出的判斷**：對工作負載而言最便宜的——用於比較的黃金答案、使用者為每個輸出評分的簡短評分標準，或自動檢查器（測試通過、JSON 驗證、必填欄位存在）。當沒有更便宜的選項時，模型評分的評判是可接受的，但它本身是批准的 API 支出。
  - **執行器**：一個透過一個設定執行凍結輸入、記錄每個輸出加上 `response.usage`，並報告通過率和每項任務成本的指令碼。每個設定是一次呼叫；調整是對設定的迴圈。
  - **成本和批准**：估算它（輸入 × 設定 × 每項任務基準線成本）並在執行前取得使用者同意——這是常設批准規則下的真實 API 支出。
- 保留或還原在本地決定，根據 eval 證據。在切換之前對即時流量進行影子執行，在之後讓 eval 繼續執行，並在切換**之後**在使用量和成本報告中確認節省——只在流量可歸因的地方（步驟 1 的共享金鑰注意事項也適用於確認讀取）。
- 預期大多數槓桿不適合任何給定的工作負載。在 cookbook 的實際案例中，大多數沒有獲得一席之地——工具綱要太小不值得工具搜尋，迴圈太短不值得編輯或壓縮，沒有數值工作不值得程式碼執行——而成本上最接近的槓桿各自還回了一個正確答案。步驟 1 的分析報告存在是為了讓最佳化不是盲目的。
- 將設定繪製為得分對每項任務成本，並取 Pareto 前沿——這是切換決定的讀取來源。

## 工作負載形狀 -> 槓桿

改編自 cookbook 的要點表，用於將分析報告對應到槓桿（第 1 行的注意事項已擴展）：

| 成本在哪裡 | 嘗試 | 跳過或注意時機 |
|---|---|---|
| 相同的系統 prompt 和工具每次呼叫都被重新計費 | Prompt 快取，先自動，然後當許多獨立對話共享靜態前綴或前綴層以不同速度變化時，在靜態前綴上設定明確斷點；如果呼叫間隔超過五分鐘，使用 1 小時 TTL | 任何動態內容都在斷點上方——將該內容移到使用者輪次中。已良好讀取的快取不需要任何修改：並行批次未命中（§ 2.5）不是破壞者，而 1 小時 TTL 對間隔數小時的呼叫無效 |
| 每個 prompt 中的大型參考文件 | 移至工具或 skill 背後 | 每次呼叫都需要大部分文件而非某個章節，或 eval 顯示模型需要去尋找的規則上的案例出現失誤 |
| 許多或龐大的工具綱要 | 帶 `defer_loading` 的工具搜尋 | 在約 10K 綱要 token 以下，搜尋步驟是額外負擔 |
| 情境中的圖片、PDF 或大型檔案 | 將圖片縮減到任務所需的解析度，並對表格和 PDF 使用 Files API 加程式碼執行 | 沒有什麼可提取或計算，所以沙箱只會增加 token |
| 無界的使用者提供輸入 | 作為接收閘道的 token 計算 | |
| 龐大結果在長迴圈中堆積 | 伺服器端的情境編輯或壓縮，或在自然邊界的用戶端修剪 | 迴圈短或清除的內容仍然需要，注意每次編輯從那點起破壞快取 |
| 一個有龐大中間結果的自包含步驟 | 子 agent，可選擇使用更便宜的模型 | 決策模型需要那些中間情境才能正確判斷 |
| 長可見回應 | 用範例在 prompt 中指定輸出形狀，以 `max_tokens` 作為底線，並以停止序列哨兵提前退出 | |
| 思考和工具呼叫主導，且 eval 有餘裕 | 先降低 `effort`，然後降一個模型層並重新調整 effort | 始終是直接的能力權衡，所以每次一個等級對照 eval 降級 |
| 大多是例行案例，少數困難的 | 在較便宜驅動者上的顧問工具 | 沒有廉價訊號來閘道諮詢，讓驅動者自己識別困難案例 |
| 沒有人在等待回應 | 批次 API，必要時透過提前預取其輸入將工具迴圈展平為一個請求 | 使用者在等待，或當展平改變模型的推理方式時 |

## 步驟 4：交付成果

1. **成本分析報告和計畫**：步驟 0 的假設（範圍、品質標準、基準線）、步驟 1 的 token 分析報告，以及選擇的槓桿及其各自攜帶的測量預期值——加上刻意跳過的槓桿和原因，使下一個人不必重新辯論它們。將候選清單表標記為按節省上限排名，而非套用順序，使其不能被誤讀為差異序列。
2. **變更**：每個槓桿一個差異，使效果可歸因——在使用者批准執行的地方套用並測量（預期對比實測的每項任務成本，通過率是否保持）；在未批准的地方，或權衡槓桿仍需要 eval 的地方，留作攜帶其預期節省和已發布品質成本的提案。當沒有什麼通過排名下限時，此交付成果是「不建議進行任何更改」——這是成功的結果；直白地說出來，而不是製造一個槓桿。

**報告骨架**（章節順序和必填欄——其餘保持靈活）：

- **範圍 / 品質標準 / 基準線 / 平台**（步驟 0 假設）
- **Token 分析報告**（步驟 1）
- **排名候選清單**——表格欄：`槓桿 | 類型（免費贏 / 權衡）| 節省上限 | 資料來源（已實測 / 使用日誌 / 程式碼估算）`。上限以資料支援的單位層（步驟 1 -> 對槓桿排名）。表格說明「按節省上限排名，而非套用順序。」
- **提議的變更**——每個槓桿一個差異，按 § 2 套用順序編號（免費贏 -> effort / 預算 -> 模型），各自標記*已套用並測量* / *已提議* / *需要 eval*
- **已跳過的槓桿**及原因（包含因平台可用性而放棄的）
- **下一步 / 需要的批准**——測量預算詢問、eval 先決條件，或「不建議進行任何更改」
